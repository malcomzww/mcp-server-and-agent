## Fault model

Per-step probability, drawn independently from a seeded RNG:

| fault | p | what it stands in for |
|---|---|---|
| `misselect` | 0.16 | two tool descriptions that do not discriminate |
| `bad_args` | 0.12 | a schema the model half-read |
| `transient` | 0.20 | the network |
| `stall` | 0.10 | a model that re-emits its last plan instead of parsing the error |
| `context_bloat` | 0.24 | a tool returning a document when asked for a field |

`recovery_skill = 0.60` -- the probability
the policy acts on an error observation that names its own fix. This is
what "a better model" means operationally in this simulation.

Controls: `max_steps=8`, `context_limit=2000` tokens, `cascade_threshold=3` consecutive tool errors.

## Does supervisor beat single-agent?

**Yes, but not enough to justify what it costs, and it is dominated.**

Supervisor cuts the failure rate from 31.7% to 28.2% -- a **3.5 point** reduction. The paired bootstrap delta is **-0.035 [-0.062, -0.008]** at 95%, so the improvement is real rather than noise: the interval excludes zero. It costs **1.73x the tokens** to get it.

The reason is structural. A supervisor pays a handoff tax on every dispatch -- 3.9 handoffs per run here -- because each worker starts cold and must be told the task and the tool list again. What it buys is *containment*: a fresh worker context means an error at step k does not poison step k+1.

But containment is available more cheaply. **Both `pipeline` and
`reflexive` beat `supervisor` on failure rate *and* on tokens** -- the
script asserts this and exits non-zero if it stops holding:

| topology | failure rate | tokens/run | dominates supervisor? |
|---|---|---|---|
| `supervisor` | 28.2% | 4,238 | -- |
| `pipeline` | 21.2% | 3,244 | yes, on both axes |
| `reflexive` | 4.5% | 2,996 | yes, on both axes |

So the answer to the repo's question is: supervisor beats single-agent,
and loses to two simpler things. Paying 1.7x for the third-best outcome
is the finding.

## What actually worked

`reflexive` -- one agent plus a *single* reflection-and-retry pass -- cut failures to **4.5%**, a paired delta of **-0.272 [-0.307, -0.237]** against single-agent, for 1.22x the tokens.

The retry is not a blind rerun: it inspects the trace, drops the steps
that already succeeded, and re-attempts only what is outstanding. That is
why it is cheaper than the supervisor while working better.

The comparison it was built to make: **supervisor and reflexive both add
tokens, but only one adds a genuinely new capability.** A second agent
re-does work in a clean context. A second *attempt* uses what the first
attempt learned. Under this fault model the second is worth more.

## Which failure modes each topology suffers

Counts over all runs, not rates, so the columns sum to the failures above.

| topology | `error_cascade` | `step_cap` |
|---|---|---|
| `single` | 116 | 74 |
| `supervisor` | 118 | 51 |
| `pipeline` | 126 | 1 |
| `reflexive` | 23 | 4 |

The shapes differ more than the totals do. `pipeline` almost eliminates step-cap failures (1 versus 74 for single-agent) because each stage gets a fresh step budget, so one stalling stage cannot consume the whole run's allowance -- but it still cascades as often as anyone else, because a failed stage has no re-planner behind it. `supervisor` gets a weaker version of the same containment for considerably more money.

At this fault rate **no topology exhausts context** -- the column is absent because every count is zero. The `context_bloat` fault fires often (24% of steps) but the 2000-token window absorbs it within an 8-step cap. Context exhaustion is reproducible here, and the taxonomy carries a seed for it, but it needs a tighter window than the headline configuration uses. The script asserts the supervisor's count stays at zero, since fresh per-worker contexts are the one place its architecture is structurally protective.

## Does the ranking survive a different fault rate?

All five fault probabilities multiplied by a common factor,
40 trials per cell. A ranking that only holds at one fault
rate is not a finding about topologies.

| scale | `single` | `supervisor` | `pipeline` | `reflexive` |
|---|---|---|---|---|
| 0.5x | 4.2% | 3.3% | 2.1% | 0.0% |
| 0.75x | 17.5% | 12.1% | 8.3% | 0.0% |
| 1.0x | 30.8% | 25.8% | 18.3% | 4.2% |
| 1.5x | 58.8% | 54.2% | 44.6% | 20.4% |
| 2.0x | 80.4% | 78.8% | 72.5% | 51.7% |

The ordering `reflexive < pipeline < supervisor < single` holds at every
scale tested, which the script asserts. The *gaps* narrow as faults rise:
at 2x every topology is failing most of the time, and no amount of
routing rescues a step that fails 40% of the time. **Topology is a
second-order effect. Tool reliability is the first-order one** -- which
is an argument for spending the effort on the tools, not the graph.

## Limitations

- **No LLM was involved.** The policy is scripted and the faults are
  drawn from a distribution someone chose. The numbers are a property
  of that fault model, and a different fault model gives different
  numbers. What transfers is the *shape* of the result, not the values.
- **The fault rates are uncalibrated.** Nothing here establishes that
  any real model misselects a tool 16% of the time. Calibrating them
  needs the live runs this repo deliberately does not do.
- **Token counts are synthetic**: a fixed charge per step plus
  `len(text)//4` for observations. Consistent across topologies, so the
  ratios are meaningful; the dollar figures forecast nobody's bill.
- **Six tasks, one tool server, one task shape.** All six are
  search-then-fetch-then-aggregate. A topology that shines on
  genuinely parallel work would not show it here, and that is exactly
  the case where a supervisor is supposed to win.
- **`reflexive` gets one retry; the others get none.** That is the
  comparison being made on purpose, but it does mean part of its
  advantage is the retry rather than the reflection.
